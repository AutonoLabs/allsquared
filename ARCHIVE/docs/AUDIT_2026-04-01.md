## 1. SECURITY

---

SEVERITY: Critical
FILE: server/routers.ts
ISSUE: `auth.syncClerkUser` is a `publicProcedure` — any unauthenticated caller can invoke it with an arbitrary `clerkId` and either create a rogue user account or overwrite an existing user's name and email.
FIX: Change to `protectedProcedure` and verify that `input.clerkId` matches `ctx.user.clerkId`; reject requests where they differ.

---

SEVERITY: Critical
FILE: server/routers/payments.ts
ISSUE: `handleWebhook` is a `publicProcedure` that accepts arbitrary event payloads (type `z.any()`) with no Stripe signature verification, allowing any caller to inject fake payment events (e.g., fake `payment_intent.succeeded`) and manipulate subscription/payment state.
FIX: Remove this tRPC procedure entirely; all Stripe webhook processing must go through the dedicated `/api/webhooks/stripe` Express endpoint (which already does HMAC verification) rather than exposing it as a public tRPC mutation.

---

SEVERITY: Critical
FILE: server/routers/escrow.ts
ISSUE: `handleWebhook` (Transpact webhook) is a `publicProcedure` with no signature verification, allowing any caller to forge `transaction.deposited` or `transaction.released` events and manipulate escrow state.
FIX: Remove as a tRPC procedure; move handling to the Express `/api/webhooks/transpact` endpoint and implement HMAC/shared-secret verification against `x-transpact-signature` (currently read but ignored).

---

SEVERITY: Critical
FILE: server/routers/signatures.ts
ISSUE: `handleDocuSignWebhook` is a `publicProcedure` with no DocuSign signature verification, allowing any caller to forge `envelope-completed` events and mark contracts as `active` without actual signatures.
FIX: Remove as a tRPC procedure; route through the Express `/api/webhooks/docusign` endpoint and verify the DocuSign HMAC-SHA256 webhook signature using the `X-DocuSign-Signature-1` header.

---

SEVERITY: Critical
FILE: server/_core/index.ts (lines ~240-265)
ISSUE: The Transpact and DocuSign Express webhook handlers read the body and immediately return `{ received: true }` without calling any business logic — escrow and signature state are never actually updated via these endpoints despite HMAC infrastructure being present for Stripe.
FIX: Implement full webhook routing in both handlers (mirroring the Stripe handler pattern) including HMAC verification and delegation to the respective router logic.

---

SEVERITY: High

SEVERITY: High

## 4. PERFORMANCE

---

SEVERITY: High
FILE: server/routers/contracts.ts
ISSUE: `contracts.list` and `contracts.stats` both call `getUserContracts(ctx.user.id)` which fetches **all** of the user's contracts from the DB, then filters, sorts, and paginates in application memory — O(n) DB scans on every page load.
FIX: Push filtering (`WHERE status = ?`), sorting (`ORDER BY createdAt DESC`), and pagination (`LIMIT ? OFFSET ?`) into the SQL query using Drizzle's `.where()`, `.orderBy()`, `.limit()`, and `.offset()` — match the pattern already used in `admin.ts`.

---

SEVERITY: High

ISSUE: No secondary indexes are defined on any table — high-frequency query columns like `contracts.clientId`, `contracts.providerId`, `contracts.status`, `milestones.contractId`, `notifications.userId`, `escrowTransactions.contractId`, `signatures.contractId`, and `auditLogs.userId` are all unindexed, causing full table scans.
FIX: Add Drizzle `index()` definitions on all foreign key and commonly-queried columns and run a new migration; at minimum: `contracts(clientId)`, `contracts(providerId)`, `milestones(contractId)`, `notifications(userId)`, `escrowTransactions(contractId)`, `signatures(contractId,status)`.
